# Global Starship accounting · integration work

The $1 billion mission tracks verified game-created lifetime income. It does not deduct cash. The existing room Mars fund remains separate and its stored `mars-fund` is retained. Income already earned before the durable source journal exists cannot be reconstructed reliably from cash or delivery totals, so the global counter begins at the journal's release boundary.

## Durable boundary

- Before accepting income, every player needs a server-issued durable earnings identity, including guests. A recovered or newly saved driver must retain its guest contribution without replaying it into a second global identity. Guest attachment and its failure recovery still need implementation and end-to-end tests.
- Each credit carries a server-derived source ID, category and amount. A receipt, the wallet and progression mutation, the identity's monotonically increasing eligible-income total and sequence, and pending reconciliation must commit together. Retrying the same source must not credit cash twice; reusing its ID with different content is an error. Accepted orders need persistent IDs; a UI `lastReward`, cash delta, clock timestamp or room-local player ID is not a durable receipt.
- One-time achievements and other verified game-created income count toward the goal. Transfers, sales, gifts, loans, refunds and old Mars donations do not. The event multiplier applies only to eligible repeatable activity and cab income; it does not apply to achievements, check-ins or checkpoints.
- A durable identity outbox sends `reconcile({driverId, sequence, total, name})` to the single global `Starship` object. The absolute committed total permits coalescing and retry after a lost response. The global object rejects conflicting equal sequences and regressions and applies only the new difference. The outbox acknowledges the captured sequence, retains later commits and reschedules failures beyond Cloudflare's automatic alarm retry limit. The player's committed wallet must not depend on the global service being available.
- A global object is intentionally serialized for this single shared objective. The counter is eventually reconciled; a UI must distinguish its last confirmed amount from pending local earnings. Measure wallet, room and reconciliation behavior under real gameplay load before claiming capacity.

## Launch and events

The first reconciliation reaching the goal atomically stores one completion time, launch ID and launch time 30 seconds later. It freezes the names and amounts shown in the launch roll, which is queried with keyset pagination. Lifetime accounting continues after completion. Replay is local presentation; it must not mutate ownership or the global launch. A live launch takes precedence over a replay or the older room animation, and driving remains available. Rooms need to distribute the same launch epoch and a server clock sample so clients can advance it using a monotonic clock.

A verified Dome win starts or refreshes a 1.5× room event for 10 minutes after the triggering match pays. A developer schedules a 2× global event for 30 minutes; both combine to 3×. Windows are UTC half-open intervals. Room payouts must use authoritative event state at payment, and a room that cannot refresh an expired global-event lease must defer dependent payouts. Cab accrual splits at every applicable event boundary and durably carries the remainder with the settlement and wallet credit. Historical windows must remain available until dependent cab periods settle.

The global ledger, bonus arithmetic, client clock helper and event coordinator in this worktree are independent components. They are not yet wired into rooms, driver profiles, guest identities, a developer control surface or the game UI. The journal currently handles only one source per transaction: it must support an atomic, idempotent batch before a delivery can safely pay a fare and multiple awards together. Its latest synchronous-KV changes are untested. The unbound panel in `drafts/starship-panel.ts` is unfinished, unstyled and unverified; restore it to `src` when development resumes. Protocol, contracts, live room tests, desktop and touch checks, and deployment verification remain necessary after the saved-driver and earning-source contracts land.

Work is paused while the performance baseline is established. This checkpoint is not a release candidate.
