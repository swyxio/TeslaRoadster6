# Global Starship accounting · integration work

The $1 billion mission tracks verified game-created lifetime income. It does not deduct cash. The existing room Mars fund remains separate and its stored `mars-fund` is retained. Income earned before the durable wallet exists cannot be reconstructed reliably from cash or delivery totals, so the global counter begins at that wallet's release boundary.

## Durable boundary

- Before accepting income, every player needs a server-issued durable earnings identity, including guests. A recovered or newly saved driver must retain its guest contribution without replaying it into a second global identity. Guest attachment and its failure recovery still need implementation and end-to-end tests.
- Each credit carries a server-derived source ID, category and amount. A receipt, the wallet and progression mutation, the identity's monotonically increasing eligible-income total and sequence, and pending reconciliation must commit together. Retrying the same source must not credit cash twice; reusing its ID with different content is an error. Accepted orders need persistent IDs; a UI `lastReward`, cash delta, clock timestamp or room-local player ID is not a durable receipt.
- One-time achievements and other verified game-created income count toward the goal. Transfers, sales, gifts, loans, refunds and old Mars donations do not. The event multiplier applies only to eligible repeatable activity and cab income; it does not apply to achievements, check-ins or checkpoints.
- The wallet integrator's `DriverProfile` outbox sends an absolute `eligibleIncome` total to the existing `GlobalIncome` object. Its existing `income:<driverId>` high-water marks and `total` are canonical. Retrying or sending an older total cannot add it twice. A newer pending value survives acknowledgement of an older one. Never re-credit those balances into a second object. Explicit alarm recovery beyond platform retries and source-level reversals need to be completed before release.
- A global object is intentionally serialized for this single shared objective. The counter is eventually reconciled; a UI must distinguish its last confirmed amount from pending local earnings. Measure wallet, room and reconciliation behavior under real gameplay load before claiming capacity.

## Launch and events

The first reconciliation reaching the goal atomically stores one completion time, launch ID, frozen launch total and launch time 30 seconds later in the canonical object's storage. A copy-on-write snapshot freezes each existing contributor's confirmed amount on their first subsequent credit, avoiding an unbounded crossing-time scan. The current prototype's bounded, opaque-cursor roll includes contributors confirmed at crossing; it cannot yet include outboxes that were already committed but still pending then. That gap must be resolved before release. Anonymous names and amounts are private on the roll, and public names can be opted into or hidden again. A counter already over the goal at cutover gets an explicitly labeled snapshot with unknown historical crossing and no invented launch. Lifetime accounting continues after completion. Replay is local presentation; it must not mutate ownership or the global launch. A live launch takes precedence over a replay or the older room animation, and driving remains available. Rooms need to distribute the same launch epoch and a server clock sample so clients can advance it using a monotonic clock.

A verified Dome win starts or refreshes a 1.5× room event for 10 minutes after the triggering match pays. A developer schedules a 2× global event for 30 minutes; both combine to 3×. Windows are UTC half-open intervals. The room-economy event store reserves a server-verified win and its prior rate before its payout. The host must commit the triggering match's resolved payout idempotently, then publish the reserved win; it must recover interrupted reservations before allowing later payouts or cab settlements through. Other drivers' physics must continue. An observation fence prevents a later win from changing a previously returned payout or history page. Equal-millisecond operations are ordered by moving a subsequent win one millisecond forward; a win more than one millisecond behind observed earnings is rejected, so the host must reserve it before later observations. Room payouts must use authoritative event state at payment. A global lease establishes rates only within its issued half-open interval; older timestamps require complete paginated history or must be deferred. Cab accrual splits at every applicable event boundary and durably carries the remainder with the settlement and wallet credit. Historical windows must remain available until dependent cab periods settle.

The canonical-storage extension, room-event store, bonus arithmetic, client clock helper, panel and global-event coordinator in this worktree are still unbound prototypes. They are not yet wired into the wallet integrator's `GlobalIncome`, rooms, guest identities, a developer control surface or the game UI. Source-level batches and reversals need to extend the actual committed wallet contract. Protocol, contracts, live room tests, desktop and touch checks, and deployment verification remain necessary after the saved-driver and earning-source contracts land. This branch is not a release candidate.
