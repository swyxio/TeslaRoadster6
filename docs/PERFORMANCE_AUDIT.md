## Architecture

The browser renders Three.js and immediately predicts the controlled car only where prediction is safe; authoritative snapshots reconcile it. The client aims to send current inputs at 20 Hz, preserving the fractional remainder between render frames and dropping missed intervals instead of sending a burst. A room is one active Cloudflare Durable Object: it consumes current inputs and simulates at a nominal 20 Hz, then sends recipient-filtered, complete JSON snapshots at a nominal 10 Hz. Ambient cars outside the recipient's interest radius are omitted; players and their cars remain visible. A room timer does not hibernate while the simulation runs. Chat uses a separate Durable Object. The per-room Mars fund persists; ordinary room simulation and personal game progress do not.

This pass removes the unused local solo simulation and the full release history from the game entry point, starts with an empty presentation state until the first room snapshot, and defers road-graph construction until a route is requested. The first valid route request pays that one-time graph construction cost in the Worker. Repeated police, pickup and collision scans now avoid work when candidates are clearly irrelevant. These changes preserve authoritative outcomes; they do not change the wire protocol. Historical release notes retain the behavior they described at the time.

## Measurements

- The minified game entry bundle changed from 929.90 kB / 274.68 kB gzip to 903.28 kB / 265.82 kB gzip. CSS is separate. This is a build size, not a measurement of cache hits or actual transferred bytes. The remaining large-chunk warning is real; Three.js and the game still load together.
- In two paired, deterministic 64-driver, 500-tick simulation runs, baseline CPU time was 3,026–3,499 ms and the optimized version was 2,671–2,812 ms. Every run produced the same final-world SHA-256 (`92bfd53142b649e6cffbfc73b7f660650699101f2633a88662d762e39647134a`). This isolates a synthetic simulation scenario and includes process/background CPU, not networking, rendering, or all possible game states.
- A Node/tsx startup CPU profile identified road-graph construction in module initialization. Three alternating dynamic-import samples were 167–267 ms baseline and 94–154 ms with lazy construction. Transform overhead and host scheduling are included; these are not browser startup times.
- In two short same-host 64-client load runs per build, all clients connected and saw all players, but simulation advanced only 3.8–6.4 seconds in eight wall seconds. One pair favored the baseline and the other slightly favored the change. These runs also loaded the client machine with JSON parsing; a server reload may have affected one run. They establish neither a performance gain nor a playable capacity. The 64-seat default is a connection/gameplay limit, not a throughput guarantee; a busy room can slow down before it is full.
- Two local two-client input-to-authoritative-displacement measurements were about 194–212 ms for driver and peer. They include vehicle acceleration and snapshot cadence; they are not screen feedback latency, internet measurements, or percentiles. Ground prediction makes the local presentation responsive in supported circumstances; collisions, flight and other barriers intentionally defer to authority.
- In a local two-client room, sampled median WebSocket frame sizes were 45,767 bytes without compression and 3,303 bytes with negotiated `permessage-deflate`. These include WebSocket frame headers, not TCP/IP overhead, and are not a measurement of production transport or a 64-player room.
- On a short desktop Chrome playtest at one position, opt-in diagnostics showed roughly 120 FPS, 9.2 ms p95 frame interval, 3.8 ms p95 CPU callback work, 246 draw calls and 192,810 triangles. These numbers are scene-, device- and load-dependent; CPU callback time does not measure GPU completion. Desktop driving worked. Portrait and landscape layouts rendered in emulation, but automated touch did not activate reliably in this session, and no physical device was tested.
- One sequential same-host test/build comparison measured 21.08/18.47 seconds for the baseline and 13.21/9.16 seconds for this branch, respectively. The baseline contains four additional solo-mode tests; load varied and there was only one run of each. Treat these as build-health observations, not reliable speedup estimates.
- With the 447-test suite, one run each with test concurrency capped at four and eight took 20.36 and 15.18 seconds respectively; the uncapped run took 13.21 seconds. The host was contended, so this does not establish a portable concurrency optimum. The default remains unchanged.

## Reproduce

1. Run `pnpm test` and `pnpm build`. The latter includes browser and Worker typechecks and the static blog/changelog build. Record wall time, host load and bundle gzip size over several clean, alternating runs before attributing a change.
2. `pnpm exec tsx scripts/bench-simulation.ts 64 500` measures the deterministic in-process workload and prints its final-state hash. Compare matching source, player count, ticks and runtime.
3. Start local Wrangler and use `pnpm exec tsx scripts/load-room.ts http://localhost:8787 64 10`. It is deliberately restricted to localhost. It measures decoded JSON received by synthetic clients, not network-wire bytes; same-host contention affects the result. `scripts/measure-room-compression.ts` samples locally negotiated frame sizes separately. `tests/driving-latency.integration.ts` observes server-confirmed displacement, not display latency.
4. Open the game with `?perf=1`; the game publishes a bounded rolling sample in `document.body.dataset.teslandPerf` every 60 frames. `frameP95Ms` measures animation-frame intervals, `cpuP95Ms` measures the synchronous game callback, and renderer draw calls/triangles describe the last frame. `pickupMeshes` and `visiblePickups` report cached and currently visible pickup markers. Turn the flag off for normal play; use a real browser performance trace and GPU/device tools for diagnosis.

## Priorities for the next pass

1. **Room scaling:** profile Worker tick and serialization time, compressed outbound bytes, snapshot gaps and authoritative input acknowledgement under a sustained, authorized preview load generated from separate machines and realistic regions. Test jitter, loss, reconnects, full-room handling, collision corrections, ferries, flight and mini-games. Establish a safe room size and cost before raising the cap. Full snapshots and per-client filtering are candidates for optimization, but delta encoding or broader interest filtering need explicit protocol versioning, resynchronization and correctness tests; do not implement them solely from socket counts.
2. **Rendering and touch:** profile representative dense city, flight and mini-game scenes on real desktop and mobile GPUs, with sustained frame times, memory and thermal behavior. Verify every touch control and dialog on physical portrait and landscape devices. The emulated layout and CPU-only frame metric above are not substitutes.
3. **Budgets and automation:** collect repeated, isolated CI measurements using the local baseline for build/test time and startup JavaScript, then extend measurement to frame time and server tick progress. Set budgets after collecting stable data. Avoid splitting the bundle merely to silence Vite: defer genuinely optional features only when the first interaction and caching tradeoffs are measured.
4. **Gameplay still underdeveloped:** a full room offers retry or a named room, not a queue. The shared $1 billion Mars goal persists per room, but current payouts are intentionally far too small to reach it in ordinary play; higher-paying levels are future work. Saved chat identity does not restore personal money or achievements. Shooting and death/respawn remain design work, not implemented features.

Use [multiplayer research](MULTIPLAYER_PERFORMANCE.md) and [verification](VERIFICATION.md) for earlier experiments and their limitations. Never compare samples across map, protocol, host load or workload changes as if they were a controlled benchmark.
